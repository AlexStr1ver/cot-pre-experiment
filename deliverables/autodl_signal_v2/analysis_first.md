# 首轮信号测量结果审计与下一步判断

本报告针对用户上传的 `infty_signal_first_ia1mUMM1_return.zip`，只读核对结果与已上传native20源文件。统计对应两个开发题的四个很短前缀，不是四道独立题目。

## 当前结论

**首轮工程验证通过，可以进入长前缀与对齐信号定义的验证。** 运行正常退出（exit=0），4/4位置完成，无跳过。环境检查、6项旧控制逻辑自测、7项新CPU测试均通过。四个真实checkpoint/BF16/GPU样本中，分块KV回放与完整eager参考的H及最后token logits报告为完全一致；逐项重算归一化、ΔH和C也一致。

这些结果验证了“能够可靠取出所定义的信号”。尚未执行摘要/重置干预，也没有联合规则、端到端比较或泛化证据。不能据此声称idea有效、无效或具有顶会级贡献。

四个短答案都不正确（题1标准答案6，题6标准答案28）。它们是128/256 token处的早期探测，不能视为完整解题准确率，更不能检验尚未运行的摘要策略。题6的C上升且归一化H下降，答案仍错，说明这些信号方向本身不是正确性保证；仅两个位置也不能评估它们是否能预测摘要收益。

C依旧受格式概率影响。例如题1/cut128的内容token“4”概率为0.294506，包含闭合括号及换行的下一token概率为0.975324，均值变成0.634915。保留旧定义便于兼容，但后续需单列内容/格式token范围，不能把该均值称为语义正确概率。

题6存在一个值得记录的长度归一化现象：raw entropy sum由5569.20升至5715.71，而除log(keys)后的H由986.49降至949.68（−3.732%）；keys由283增至411。它不说明公式错了，而是说明归一化会改变变化方向，后续必须保存raw/normalized H并控制长度/阶段混淆。

## 成本与硬件

- 当前GPU报告为 **NVIDIA GeForce RTX 2080 Ti**，总显存21.49 GiB；历史实验记录是RTX4090。此次时延不能直接与历史4090时延计算加速比。
- torch2.6.0+cu124、transformers4.51.3、vLLM0.8.5；本轮实际用Transformers eager。
- 四点replay总计1.374秒，独立probe总计1.179秒，额外完整参考检查0.561秒；模型加载2.511秒。这些分项不是端到端策略耗时。
- 峰值allocated最大3.458 GiB，reserved最大3.703 GiB。此次峰值包含短序列完整参考检查。183–411输入token处的显存不能直接外推4k前缀。
- torch.cuda.is_bf16_supported返回true不一定代表原生BF16 tensor-core路径；下一版记录device capability及including_emulation=False结果，避免把API可运行与硬件加速混同。无需仅因GPU名字而推翻已经成功的数值结果。

## 下一步建议

1. 先做一个约4k前缀canary，实测显存、耗时、有限值和概率行质量；设置保守的显存/时间门限，失败保留诊断，不自动扩大实验。
2. 然后固定同一组题目，至少三个长度附近的自然边界，避免v1文档里分别取每个长度前三题导致题集变化。按原20题全部候选无标签筛选，1024/2048/4096均可用的题号为1、6、8、10、11、12、15、19；按题号取前三题得到1、6、8，实际cut分别为(1041,2104,4103)、(1055,2092,4203)、(1084,2055,4173)。
3. 新版保留v1 tail-window作为兼容诊断，同时明确实现/记录ASAG式probe-window定义及相对首测点基线。当前固定边界仍不是ASAG的Wait ATP，故名称保持ASAG-style；不能直接套其阈值。
4. 每个样本保存相同prefix哈希、query窗口与probe token IDs、raw与normalized H、q/k、逐token概率、格式范围、额外prefill与探测成本。无答案闭合时C为null；首测点ΔH=0仅是初始化。
5. 暂不调阈值或启用在线摘要控制器。完成长前缀数值/成本检查后，再把同位置信号与已有A/B/C动作结果连接，必要时补小规模公平budget配对。最终需要区分“直接交付答案”和“压缩后继续”的收益。
